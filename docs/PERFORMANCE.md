# 配图性能与取舍

默认 representative 模式以图文博客中的参考画面为目标，允许漏掉短暂 PPT 页面。正文仍完整处理；图片保存完整原始尺寸。以下是开发阶段同一台 20 逻辑 CPU 机器的本地样本测量，不是通用性能保证。

## 配图阶段

只比较缓存视频的配图，不含下载、ASR 或 LLM。旧密集模式与代表模式的目标不同，且不是同时测量，不能解释成同等精度的纯算法加速。

| 内容类型 | 时长 | 密集模式 | 代表模式 | 图片数（密集 → 代表） |
| --- | ---: | ---: | ---: | ---: |
| 混剪 | 10分08秒 | 87.59秒 | 6.30秒 | 9 → 7 |
| 图表讲解 | 16分18秒 | 272.88秒 | 7.34秒 | 84 → 10 |
| 滚动文档 | 39分53秒 | 1892.14秒 | 13.59秒 | 244 → 24 |
| 长课程 | 100分钟 | 1027.77秒 | 26.16秒 | 176 → 57 |

旧流程的文字密集帧 OCR 单张曾耗时 7–16 秒；大量逐帧 OCR 是主要瓶颈。代表模式先稀疏选择少数画面，默认完全跳过 OCR。候选分析用小图，最终仍导出完整尺寸。

同一代表算法、同一滚动文档的控制实验：单任务 **52.06秒**，四任务 **13.84秒**，约 3.76 倍；24 张最终图片逐字节一致。没有独立测量 CPU 利用率，不宣称所有核心均跑满。可选 OCR 在一段 10 分钟混剪上将总耗时从 6.30 秒提高到 13.94 秒，不能据此预测文字密集内容。

## 完整流程

同一 100 分钟课程只复用视频和原始字幕，51 个润色块、标题及配图重新生成，曾测得总耗时 **143.95 秒**：润色 126.98 秒、标题 15.22 秒，配图 28.42 秒与文本处理重叠。下载与 ASR 未计入，供应商响应速度会显著改变结果，不能承诺每次两分钟完成。

该次文本仍有原文回退及数字告警，strict 返回 2。速度测量不等于质量通过，也没有为提速降低正文校验阈值。全缓存且禁止网络的后续恢复约 0.44 秒，Markdown 哈希与修改时间未变。

## 自行复现

先在自己的工作目录生成视频缓存，再用同一解释器运行：

```sh
python scripts/benchmark_slides.py BV1234567890 --workspace ../my-bilidraft-work --workers 1
python scripts/benchmark_slides.py BV1234567890 --workspace ../my-bilidraft-work --workers 4
python scripts/benchmark_slides.py BV1234567890 --workspace ../my-bilidraft-work --ocr
```

替换虚构 BV；详细模式用 `--mode detailed`。每次写入新的 `notes/_benchmarks/` 子目录，不覆盖现有讲义，不调用 LLM。可用 `--text-dir` 指定已验证的讲义目录，仅复用其 clean/outline 进行配图预览。

报告的 worker_seconds 是线程累计工作时间，wall_sec 才是阶段实际等待。公开反馈时去掉课程 ID、标题、路径、原始文本和机器个人信息；保留配置、版本、时长与耗时即可。
